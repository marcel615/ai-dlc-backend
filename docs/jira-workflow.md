# Backend Jira 작업 추적

활성 서비스의 `work_tracking.provider: jira`에서만 이 절차를 적용한다. 생략 또는 `github_projects`면 기존 GitHub Projects 절차를 유지한다. 알 수 없는 provider나 필수 값의 누락은 중단해 보고한다. Jira 실패를 GitHub Projects로 대체하지 않는다. GitHub는 코드·PR·CI를 담당하고 공식 계약은 설정된 Specs 저장소를 읽기 전용으로 참조한다.

## 설정과 선정

활성 서비스의 `jira.site_url`, `project_key`, `issue_types.candidate`, `issue_types.implementation`, `statuses.candidate`, `statuses.backlog`, `statuses.ready`, `statuses.in_progress`, `statuses.in_review`, `statuses.done`, `role_labels.backend`, `approval`, `priority_order`와 Backend 저장소 및 기준 브랜치를 작업에 필요한 범위에서 읽고 실제 Jira 프로젝트·유형·상태·라벨·접근 권한과 대조한다. `approval`은 `user_transition_to_backlog`를 사용한다. 설정은 Orchestrator와 같은 구조를 사용한다. 상태 이름이 중복되거나 값·권한·전환을 확인할 수 없으면 보류한다. Jira 연결 도구를 우선 사용하고 목록의 모든 페이지를 확인한다. 상태 존재만으로 전환 가능하다고 가정하지 않는다. 비밀값은 기록하지 않는다.

새 작업을 선정할 때는 설정된 프로젝트에서 유형이 `jira.issue_types.implementation`인 Task 중 상태가 `jira.statuses.ready`이고 `jira.role_labels.backend` 라벨이 있는 작업만 선정한다. 새로 직접 지정한 작업도 같은 조건을 확인한다. Epic, 후보, 다른 역할이나 다른 프로젝트는 제외하며 조건을 확인할 수 없는 작업은 보류한다. 사용자가 직접 `ready`로 옮기며 Backend는 이 전환을 수행하지 않는다. 기존 작업의 재개에는 `ready`를 요구하지 않고 아래 재개 절차를 따른다.

기존 진행 작업이 있으면 새 작업을 시작하지 않는다. 후보의 본문·사용자 결정과 출처·관련 관계 및 선행 조건을 확인하고 미결정 또는 충족 여부가 불명확하면 보류한다. 선행 작업이 열려 있으면 제외하며 조회 실패를 관계 없음으로 취급하지 않는다. 가능한 후보는 `jira.priority_order`의 순서, 생성 시각이 오래된 순, 안정적인 이슈 ID 순으로 선정한다. 우선순위가 없으면 마지막에 두고 설정에 없는 우선순위는 보류한다. Jira 키·제목·선정 근거와 결정 출처를 기록해 기존 설계·품질 게이트에 전달한다.

## 상태와 PR

1. 새 작업의 실제 착수 직전에 해당 Task의 프로젝트·유형·라벨·현재 `jira.statuses.ready` 상태와 가능한 전환을 다시 확인한다. `jira.statuses.in_progress`로 전환하고 같은 Task를 재조회해 결과를 확인한다. 실패하거나 결과가 불명확하면 재조회해 이미 성공한 변경을 반복하지 않고, 확인되지 않으면 중단한다. 재개에서는 이 신규 착수 전환을 반복하지 않는다.
2. 설정된 Backend 저장소와 대상 브랜치로 검토 가능한 PR을 연 후 해당 Task에 PR URL을 기록한다. Task를 재조회해 정확한 링크가 남았는지 확인한 뒤 `jira.statuses.in_review`로 전환하고 다시 조회한다. 링크나 상태 확인에 실패하면 중단하고, 재개 시 이미 기록된 링크·상태를 확인해 중복 기록을 피한다.
3. 사용자의 작업 마무리 요청을 받았을 때만 Task에 연결된 PR을 GitHub에서 조회한다. PR의 저장소와 대상 브랜치가 설정된 Backend 저장소·기준 브랜치와 일치하고 실제 merge된 사실을 확인한다. 닫힘이나 머지 예정만으로 완료 처리하지 않는다. 연결된 PR이 여러 개이거나 대상이 불명확하면 추측하지 않고 확인한다. 확인된 해당 Task만 `jira.statuses.done`으로 전환하고 재조회한다. 전환 불가·조회 실패·불일치는 중단해 보고한다.

전환 전 현재 상태·가능한 전환·필요 권한을 확인하고, 각 쓰기 후 실제 결과를 확인한다. 기존 완료 상태라면 변경을 반복하지 않는다. Jira Automation은 설정하거나 성공했다고 가정하지 않는다. PR 머지는 사용자가 직접 수행하며 Task 완료는 Epic이나 기능 전체의 완료를 의미하지 않는다.

## 범위와 재개

### 기존 작업 재개

작업 기록을 단서로 같은 Task의 프로젝트·유형·백엔드 라벨·현재 상태와 연결된 PR, Git 브랜치·변경 사항을 재조회한다. 기존 작업임을 확인할 수 없거나 상태·PR·기록이 충돌하면 보류하고 보고한다. `jira.statuses.in_progress`에서는 상태 변경 없이 남은 작업을 이어간다. `jira.statuses.in_review`에서는 `in_progress`로 되돌리지 않고 기존 PR의 리뷰·수정·검증을 이어간다. PR이 실제 머지됐다면 사용자의 마무리 요청을 기다리고 위 완료 절차를 따른다. 그 밖의 상태나 PR 연결이 불명확하면 추측해 변경하지 않는다. 동시 실행을 막는 잠금이나 원자적 선점은 제공하지 않는다.

## 후보 등록과 정제

`feature-discovery` 지시에서 공식 요구사항·기존 구현·열린/닫힌 GitHub Issue와 Jira 작업·후보를 확인해 백엔드 단독 아이디어의 중복과 충돌을 검토한다. 단독 범위, 접근이나 중복 확인이 불가능하면 생성하지 않는다. 사용자 요청당 유효 후보를 최대 3개까지 설정된 프로젝트의 `jira.issue_types.candidate` Task로 등록하고 `jira.statuses.candidate`에 둔다. 후보 본문에 고유 Candidate ID, 목적·예상 효과·차이·미결 사항·출처를 기록한다. 생성 상태가 다르면 가능한 전환과 권한을 확인해 후보 상태로 옮기고 키·유형·상태·본문을 재조회한다. 결과가 불확실하면 Candidate ID로 재조회하여 중복 생성을 피한다. 후보 등록은 승인이나 개발 착수가 아니다.

`backlog-refinement` 지시에서는 자동 선정과 직접 지정 모두 후보의 목적·범위·관련 역할을 확인해 **백엔드 단독으로 끝나는 것이 확인된 후보만** 정제한다. 공통 후보나 담당 영역이 불명확한 후보는 라벨·본문을 변경하지 않고 보류하며 이유를 보고한다. 공통 후보와 Epic 관리는 Orchestrator가 담당한다. 백엔드 라벨이나 승인 상태만으로 백엔드 단독 범위를 추정하지 않는다.

사용자가 후보를 직접 `jira.statuses.backlog`로 옮긴 이력을 전환자·시각과 신뢰 가능한 사용자 계정으로 확인한다. 현재 상태만으로 승인을 추정하지 않는다. 후보로 되돌아간 적이 있으면 최신 이력의 승인 유효성을 재확인한다. 승인·후보 식별·중복·목표·접근 여부가 불명확하면 보류한다. 승인된 후보를 최대 2개까지 검토한다. 변경 직전에도 단독 범위와 상태를 재확인한다. 기존 Task의 같은 키를 유지하고 `jira.role_labels.backend`, 구현 범위·제외 범위·완료 조건 및 필요한 결정을 본문에 추가한다. 기존 본문·승인 이력·관계를 보존하고 권한을 재확인하며, 변경 후 키·유형·상태·라벨·본문을 재조회한다. 별도 Task나 Epic은 생성하지 않는다. 후보 유형이 구현 Task와 다르거나 같은 키로 유지할 수 없으면 추측하거나 새 작업으로 대체하지 않고 보류한다. 세부 결정이 남으면 사용자에게 보고하고 `backlog`에 둔다. `jira.statuses.ready` 전환은 사용자만 수행한다.

## 계약 변경 발견

기존 계약을 지키는 대안을 먼저 검토한다. 변경이 필요하면 관련 작업을 보류하고 공식 원본 링크와 확인 버전, 사유·대안과 한계·영향·수정안·필요한 결정을 로컬 `docs/current-work-log.md`에 기록하고 사용자에게 보고해 별도 계약 변경 절차로 안내한다. 이 사유를 기록하려고 Jira Task 본문이나 댓글을 수정하지 않는다. 실제 공식 원본 반영과 사용자 결정, 설계·검증을 재확인한 뒤 재개한다.
