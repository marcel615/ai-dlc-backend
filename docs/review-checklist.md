# Review Checklist

## 프로젝트와 경로

- [ ] 등록된 이름·별칭으로 대상을 유일하게 식별하고 대상 설정·Git 루트·원격 저장소 일치를 확인했는가?
- [ ] 공통 운영 파일과 대상 설정·기록·소스·Git·테스트 경로를 구분하고 하위 에이전트에 세 절대 경로를 전달했는가?
- [ ] 대상 `.github` 템플릿을 우선 확인하고 공통 템플릿을 자동 복사하거나 기존 파일을 덮어쓰지 않았는가?

## 작업 범위

- [ ] `docs/current-task.md` 범위 안에서 작업했는가?
- [ ] 불필요한 변경이 없는가?
- [ ] 작업 브랜치가 `ai-dlc.yaml`의 `development.branch_pattern` 형식인가?
- [ ] PR 방향이 설정된 작업 브랜치 → Backend 기준 브랜치인가?

## 파일 수정 권한 / 공식 계약

- [ ] 일반 개발에서 공식 계약과 AI-DLC 운영 파일의 diff가 없는가?
- [ ] README 변경은 승인된 작업 범위 안에 있고 운영 규칙·승인 조건·보호 파일의 수정 제한을 변경하거나 우회하지 않는가?
- [ ] 별도 AI-DLC 유지보수라면 사용자 승인 근거·대상 파일과 실제 diff가 일치하는가?
- [ ] 설계·로그·devlog·명시된 Skill 상태 파일은 기존 역할과 승인 범위에서 변경했고 기록으로 운영 규칙을 바꾸지 않았는가?
- [ ] 공식 요구사항·API·인증·ERD·UI 등은 설정된 Specs 원본을 읽기 전용으로 참조했는가?
- [ ] 기존 계약을 지키는 구현 대안과 계약 변경 필요성의 판단 근거를 기록했는가?
- [ ] 변경이 필요하면 Main이 사유·대안과 한계·영향·수정안·원본 링크와 확인 버전을 보고하고 관련 Issue·PR에 기존 승인 범위에서 기록했는가?
- [ ] 계약 변경이 필요한 작업은 보류했으며, 재개했다면 별도 계약 관리 결과·사용자 결정·실제 원본 반영과 설계·테스트·게이트 재검증 근거가 있는가?
- [ ] 유지보수 승인을 Specs 수정 권한으로 확대하지 않고 기존 승인·품질 게이트를 유지했는가?

## 백엔드 구조

- [ ] Controller / Service / Repository 책임이 분리되어 있는가?
- [ ] Entity를 API 응답으로 직접 반환하지 않는가?
- [ ] Request DTO와 Response DTO가 분리되어 있는가?
- [ ] Validation이 적용되어 있는가?
- [ ] 예외 응답 형식이 일관적인가?

## 가독성 / 복잡성

- [ ] 조회·검증·생성·저장·응답 변환 등 주요 처리 흐름을 위에서 아래로 따라갈 수 있는가?
- [ ] 복잡한 중첩 호출, 한 줄 조건문과 여러 문장을 압축한 표현을 피하고, 명시적인 타입과 의미 있는 이름을 사용했는가?
- [ ] record·인자·어노테이션·체이닝의 줄바꿈과 들여쓰기가 구조를 이해하기 쉽게 보여주는가?
- [ ] 클래스·패키지·Bean의 역할과 관련 설정의 위치가 명확한가?
- [ ] Security 설정의 기능과 인가 규칙 순서를 이해할 수 있고, 인증 사용자 전달 방식이 기존 인증 구조와 권한 검증에 맞는가?
- [ ] 새 추상화·설정·최적화·방어 로직이 실제 요구사항에 필요한가? 필요한 보안·정확성·동시성 보장은 유지되는가?
- [ ] 테스트가 대상이나 상황별 소주제로 묶이고, 준비·실행·검증과 기대 결과를 이해할 수 있는가?
- [ ] 변경한 설정과 실행 문서의 이름·단위·설명이 실제 사용 방식과 일치하는가?

## 설계 / 테스트

- [ ] API 구현이 `ai-dlc.yaml`의 `contracts.api`가 지정한 API 명세와 충돌하지 않는가?
- [ ] Entity 구현이 `ai-dlc.yaml`의 `contracts.erd`가 지정한 ERD와 충돌하지 않는가?
- [ ] `ai-dlc.yaml`의 기본 테스트 명령이 통과했는가?

## 자동 API 테스트

- [ ] 새 API 또는 변경된 API의 Controller / Service / Repository 테스트와 통합 테스트가 작성되었는가?
- [ ] 요청 바인딩, Validation, 정상·실패 응답, 인증·인가 및 실제 DB 쿼리를 검증했는가?
- [ ] API별 시나리오와 대응 테스트 클래스가 기록되어 있고 기존 검증 범위를 유지했는가?
- [ ] 테스트 DB·인증 설정·파일 경로가 개발·운영 환경과 격리되고 데이터·파일이 정리되는가?
- [ ] 테스트가 고정 ID, 기존 데이터, 실행 순서, 수동 서버 실행에 의존하지 않는가?
- [ ] 자동 테스트 실행 결과와 미검증 사항이 기록되었는가?
- [ ] 기존 버그·명세 불일치를 기대값 변경이나 테스트 비활성화로 숨기지 않았는가?
