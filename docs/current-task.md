## 작업과 승인 근거

- **작업:** 2026-11-12 사용자 직접 요청 — 9단계 AI-DLC 파일 수정 권한 보호 및 공통 계약 변경 대응 절차 확립. 별도 실제 Issue·Project는 없음.
- **작업 유형:** 사용자 승인 AI-DLC 유지보수. 이후 작업에서도 일반 개발 / 승인된 AI-DLC 유지보수 여부를 명시한다.
- **요청 내용:** 공식 계약과 운영 파일의 일반 개발 내 수정 제한, 기존 책임에 따른 작업 기록 수정 허용, 계약 변경 필요성의 검토·보고·기록 및 별도 절차 연결을 확립한다.
- **승인 근거:** 사용자 최초 요청의 9단계·추가 지침과 현재 저장소로 한정한 범위, 후속 지시인 `ai-dlc.example.yaml` 사용 승인. Main이 아래 설계 게이트를 통과시켰다.
- **보호 파일 변경 승인:** 이번 요청은 아래 변경 대상의 AI-DLC 운영 지침·설정 예시·템플릿 정비를 승인한다. 일반 기능 개발의 승인이 운영 파일이나 공식 계약 변경 승인을 대신하지 않는다. 이후 유지보수에서도 사용자 승인 출처와 지정 파일·변경 범위를 기록한다.
- **명시적 예외:** 실제 서비스 연결 설정이 없는 공통 템플릿 저장소의 사용자 지정 유지보수다. 예시의 가상 저장소·Project와 서비스 테스트 명령은 실행 대상으로 사용하지 않는다. Issue 자동 선정·Project 상태 전환은 수행하지 않으며, 설계·구현·독립 리뷰·기록·머지 준비 게이트는 유지한다.
- **작업 기준:** 현재 저장소의 실제 원격과 Main이 확인한 최신 `origin/main`의 `1b15c13`을 기준으로 `codex/protect-ai-dlc-contracts`에서 작업한다. 서비스용 예시 브랜치 값을 이 유지보수의 PR 대상으로 사용하지 않는다.
- **이전 작업:** 작업 트리는 시작 시 깨끗했으며 기존 current-task·current-work-log·devlog는 템플릿뿐이다. 초기화할 이전 실작업 기록은 없다.

## 공식 명세와 확인 근거

- **요구사항:** 이번 유지보수는 사용자 요청을 기준으로 한다. 서비스 개발에서는 `ai-dlc.yaml`의 `requirements`와 지정된 저장소 역할을 따른다.
- **API 명세:** 이번 작업은 서비스 API를 변경하지 않는다. 서비스 개발에서는 `contracts.api`의 공식 원본을 참조한다.
- **ERD:** 이번 작업은 서비스 DB를 변경하지 않는다. 서비스 개발에서는 `contracts.erd`의 공식 원본을 참조한다.
- **기타 공식 계약:** 인증·UI 등을 포함해 설정된 `contracts`의 각 항목을 동일한 방식으로 읽기 전용 참조한다. 필요한 항목이 없거나 경로가 불명확하면 추측하지 않고 확인한다.
- **확인 근거:** 기준 커밋의 AGENTS.md, 세 Skill, 세 Agent, README, 작업·리뷰·빠른 지시 문서, Issue·PR 템플릿과 ai-dlc.example.yaml을 분석했다. 기존 개발 Skill·Architect는 Specs 수정 권한을 부여하지 않지만 Issue 템플릿의 `API 문서 반영`은 직접 수정으로 해석될 여지가 있다.
- **명세 변경 필요성:** 공식 계약 변경 없음. 기존 승인 체계와 설정 키를 유지하고 운영 지침의 수정 권한·변경 필요성 대응만 정비한다.
- **기존 계약 준수 대안:** 이번 요청은 서비스 계약 변경 없이 운영 지침 정비로 충족한다. 서비스 작업에서는 계약에 맞춘 구현 대안과 채택·불가 사유를 먼저 기록한다.
- **계약 변경 보고와 출처:** 이번 작업은 해당 없음. 필요한 작업에서는 Main이 변경 사유·영향·수정안·대안 검토 근거를 사용자에게 보고하고 관련 Issue·PR, 사용자 결정 및 별도 계약 관리 절차의 연결·반영 근거를 기록한다.
- **미확인 사항:** 실제 서비스 공식 계약·Project는 예시 연결값이므로 조회하지 않았다. 실제 서비스 통합 동작과 외부 보호 설정의 강제 차단을 검증한 것으로 간주하지 않는다.

## 목표와 범위

- **목표:** 일반 개발, 사용자 승인 AI-DLC 유지보수, 별도 공식 계약 관리의 수정 권한을 명확하게 구분한다.
- **변경 대상:** AGENTS.md, .agents/skills의 기존 세 SKILL.md, .codex/agents의 기존 세 TOML, README.md, ai-dlc.example.yaml, docs/current-task.md, docs/current-work-log.md, docs/review-checklist.md, docs/prompts/quick.md, templates/.github의 기존 Issue·PR 템플릿 및 이번 월별 devlog다. devlog 템플릿은 변경 필요가 확인된 경우에만 정비한다.
- **구현 방향:** 공통 권한은 AGENTS.md에 두고 Skill·Agent·운영 문서에서 연결한다. 공식 계약을 유지하는 대안을 우선 검토하고 변경이 필수이면 Main 보고·Issue·PR 기록 후 영향받는 작업을 보류한다. 공식 계약은 별도 계약 관리 절차에서, 운영 파일은 사용자 승인 별도 유지보수에서만 변경한다. 별도 계약 반영 후 실제 원본과 사용자 결정을 재확인하고 설계·검증 게이트를 다시 확인한다.
- **완료 조건:** 보호 대상과 기록 예외, 유지보수 승인 근거, 계약 대안 검토·보고·기록·재개 기준이 일치하며 기존 승인 조건·역할·게이트가 유지된다. Issue 템플릿의 직접 계약 수정을 암시하는 완료 조건을 검토·기록 조건으로 전환한다.

## 제외 범위

- 다른 AI-DLC 저장소, 실제 서비스·Specs 저장소, 공식 요구사항·API·인증·ERD·UI 원본은 수정하지 않는다.
- 실제 서비스 연결값·비밀값·DB·인증·인가·필수 승인·Project 비전과 후보 승인 상태는 변경하지 않는다.
- OS 파일 권한, GitHub 보호 규칙·CI 신설, 새 계약 관리 도구·필수 설정 키 추가와 자동 배포는 제외한다. 문서상 권한 제한을 실행 환경의 강제 차단으로 보고하지 않는다.

## 설계 게이트

- **Architect 검토:** 기존 Specs 직접 수정 허용 절차는 없으며 지침 보강과 모호한 템플릿 조건 정비로 충족 가능하다. 인증·UI는 필수 키나 추정 경로를 추가하지 않고 계약 항목 전체의 참조 규칙으로 일반화한다.
- **Main 판단:** 통과. 위 파일·범위와 사용자 직접 승인 유지보수 근거, 아래 검증 계획을 승인했다.
- **사용자 결정:** 현재 저장소 유지보수와 예시 설정 사용은 승인됨. 추가 서비스 계약 변경 승인은 없으며 필요 시 별도 확인한다.
- **설계 변경:** 요구사항·범위·권한이 달라지면 변경 근거를 보고하고 필요한 승인과 게이트를 다시 확인한다.

승인되지 않은 범위는 구현하지 않는다. 기존 승인·중단 조건은 `AGENTS.md`와 해당 Skill을 따른다.

## 검증 계획과 완료 조건

- **관련 테스트:** 일반 개발의 운영 파일 수정 제한, 역할별 기록 수정 허용, 승인 유지보수의 지정 파일 수정, 기존 계약으로 구현 가능한 경우, 계약 변경이 필수인 경우의 보고·기록·보류·재개, 유지보수 승인의 Specs 권한 확대 금지를 문서 시나리오로 검토한다.
- **기본 검증:** `git diff --check`, 문서 참조·경로와 전체 diff 확인, YAML·TOML 구문 검증을 수행한다. 예시의 Gradle 테스트는 이 저장소에 실행 대상이 없어 미실행·해당 없음으로 기록하며, 서비스 개발의 기본 테스트 의무는 유지한다.
- **품질 확인:** Architect 독립 리뷰로 문서 간 모순, 수정 권한 우회, 기존 승인·품질 게이트 보존과 특정 프로젝트 하드코딩 여부를 확인한다. 실제 서비스 통합·Project 자동화·파일시스템 강제 차단은 검증하지 않는다.
- **기록:** Builder는 작업 로그에 실제 변경·검증을 기록하고 Reporter는 확인된 결과를 월별 devlog에 추가한다. 예시 연결값을 실제 실행 정보로 기록하지 않는다.
- **PR:** 현재 저장소 `codex/protect-ai-dlc-contracts` → `main`. 사용자 직접 요청에 따른 유지보수와 실제 Issue 부재를 설명하고 임의 Issue 번호를 기재하지 않는다.
- **최종 완료 조건:** 문서·구문·시나리오 검증과 독립 리뷰, devlog 반영 후 PR을 생성한다. 최종 push의 정확한 head를 기준으로 CI·필수 리뷰·브랜치 보호·충돌 상태를 확인하고 미확인·대기는 준비 완료로 표시하지 않는다. Merge는 사용자가 직접 수행한다.

검증 결과는 실제 실행 후 기록한다. 실행하지 않았거나 확인하지 못한 항목은 통과로 표시하지 않는다. PR Merge는 사용자가 직접 진행한다.
